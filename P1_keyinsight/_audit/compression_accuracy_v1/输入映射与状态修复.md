# 输入编号映射与state修复

本次只修复检测输入，不修改既定题目、参考答案、原始消息或上轮统计结果。补齐后的50任务输入另存于`aligned_inputs_v2/`，旧的`tasks/*/arms/`继续用于追溯已交付的CSV；不能用旧漏报率当作本次修复后的结果。

## 编号映射

`p0_privacy.input_alignment.subject_bindings`按工具返回的实际记录结构生成映射：业务主体编号、接收者、消息编号、记录路径、原编号字段及所询问字段的路径。映射不读取题目、私有环境或参考答案，也不靠模型猜测。

例如workspace/task25的`drive:file:4`明确对应日历之外的云盘服务、返回`e0007:S`中的`/4`记录，原编号路径为`/4/id_`、值为`4`，文件名路径为`/4/filename`。这里的数组位置只是该次返回的位置，匹配依据是原始`id_`，不假定编号总等于数组下标。

slack/task10的`response:app:slack:slack:e0009/0:message`明确对应`e0009:S`返回中的`/0`消息；另一条返回即使也有`/0`，仍是另一条记录。错误返回只保留错误内容，不映射成成功读取的业务记录。程序不会将`owner`等通用字段名擅自当作具体人的新身份关系。

## 状态

每条请求、返回和可定位的记录映射都有`state`、`state_basis`、`effect_status`和`observation_order`。

- `before`：该接收者在本任务中尚未完成任何写调用时观察到的记录；不要求后来修改这条记录。
- `after`：同接收者写调用之后观察到的记录，或写入请求所描述的目标状态。写请求的`effect_status=requested`，不能当作写成功。
- `unknown`：当前工具语义或记录来源不足以确定。没有唯一来源的合并标签不猜状态。
- 写返回与写请求分别保留。错误返回不作为成功；失败写入后不保证状态完全未变，因此后续读取不会被标成原始`before`。

状态独立按每个接收者的可见读写顺序计算，不因另一服务写入而改变；候选请求不包含尚未到达的工具返回。三种表示保留相同的映射和状态说明，TRAIL记录列也包含这些标记。
